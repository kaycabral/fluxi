# fluxi

Planejador de fluxo de caixa pessoal: um app Next.js na raiz do repo, com Supabase (Postgres e Auth). Multiusuário (qualquer conta Google entra). Sem workspaces nem turbo.

## Layout

| Caminho                                   | Papel                                                                                                                                                                                                                                        |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/app`, `src/components`, `src/hooks`… | App Next.js (App Router): `/` (landing + login), `/painel` (logado: painel/dashboard, `/painel/calendario`, `/painel/lancamentos`, `/painel/orcamento`; telas legadas no grupo `(legacy)`), `/privacidade` e `/termos` (públicas, estáticas) |
| `src/db`                                  | Schema Drizzle, queries e seed do Postgres (`@/db`)                                                                                                                                                                                          |
| `src/features/<slice>/core`               | Domínio puro da fatia (`ledger`): sem I/O, testado por unit                                                                                                                                                                                  |
| `src/features/<slice>/adapters`           | Server-only: leituras/escritas no banco e `actions/` (server actions)                                                                                                                                                                        |
| `src/features/<slice>/ui`                 | Client components da fatia (as páginas em `src/app` só compõem)                                                                                                                                                                              |
| `drizzle/`, `drizzle.config.ts`           | Migrations versionadas                                                                                                                                                                                                                       |
| `scripts/`                                | `migrate.ts` (prod/CI), `migrate-local.ts`, `local-env.ts`, `seed.ts`, `import-notion.ts`                                                                                                                                                    |
| `e2e/`, `src/**/_e2e/`, `_smoke/`         | Playwright (fixtures, specs E2E, smoke pós-deploy)                                                                                                                                                                                           |
| `supabase/`                               | Config do stack local (Docker)                                                                                                                                                                                                               |

Rotas em português (`/painel`, `/painel/...`); código em inglês.

## Regras invioláveis

1. **Next.js: leia a doc local antes de codar.** `node_modules/next/dist/docs/` é a fonte de verdade; o conhecimento de treino está defasado.
2. **pnpm apenas.** Nunca `npm`/`yarn`/`bun`.
3. **Aliases.** `@/...` pra tudo em `src/` (`@/db`, `@/lib/...`), `@e2e/*` pra `e2e/`. Nunca `../../`.
4. **Codebase em inglês.** Identificadores, comentários, mensagens de erro, logs, nomes de eventos. UI em pt-BR.
5. **ESLint: nunca desabilitar.** Sem `eslint-disable*`. Dívida antiga vive no `eslint-suppressions.json` (catraca: violação nova falha).
6. **Tipagem sem escape hatches.** Sem `any`, `as any`, `as unknown as X`, `@ts-ignore`.
7. **Primitivos UI vêm do `@cbrl/design`** (shadcn sobre Radix). Não copiar componente pro app; variante que falta vai pro `@cbrl/design` no toolkit. Exceção: `src/components/ui/form.tsx` (binding do `react-hook-form`, não é primitivo visual).
8. **Sem merge sem evidência de execução real** (spec E2E, log de `pnpm test` cobrindo o caminho, ou smoke manual descrito no PR).

## Gates

```bash

```

Ambiente local (stack Supabase via Docker): `pnpm db:start` (sobe o stack + `db:migrate:local`) → `pnpm db:env` (grava `.env.local`) → `pnpm db:seed` → `pnpm dev` (porta 3004). O login Google não roda local; use o login de teste indicado pelo `db:seed`. Studio em http://127.0.0.1:54423. Suíte Postgres: `pnpm test:integration:pg` (banco `fluxi_test` próprio, ver "Não-óbvio"); E2E: `pnpm test:e2e`. Node 26 (`engines`); com Node 22 o `readLocalSupabase` quebra.

**Portas locais** deslocadas +100 em relação ao imovil (que usa 3003 e 54320–54329), pra os dois stacks rodarem lado a lado: API 54421, DB 54422, Studio 54423, inbucket 54424, analytics 54427, pooler 54429, shadow 54420.

## Backend (Supabase)

- **Banco (Postgres)** só no servidor. No app, importe via `@/lib/db` (`server-only`, re-exporta `@/db`); `@/db` direto só em scripts, `e2e/` e testes. Tabelas com `.enableRLS()` e **sem policies** — o browser nunca lê/escreve o banco; toda escrita passa por server action (`src/features/<slice>/adapters/actions/*`, `'use server'`; ficam na fatia porque o lint de camadas proíbe `features` → `app`). Invariantes viram constraints nativas (`check`, `unique`, FK). Todo dado financeiro pertence a um usuário e toda query filtra pelo usuário da sessão.
- **Conexão**: `POSTGRES_URL` (pooler de transação, nome da integração Supabase ↔ Vercel). `fluxiDb` (`src/db/db.ts`) é o `createDrizzleDatabase` do `@cbrl/pg/drizzle` (`.db()`, `.ping()`, `.close()`, `.migrate()`): só modo password, CA do Supabase pinado, `sslmode` da URL removido. Erros do Postgres (`isUniqueViolation`, `pgErrorOf`) vêm do `@cbrl/pg`. `truncateFluxiTables` só roda no banco de teste (`assertTestDatabase`).
- **Migrations**: `pnpm db:generate` gera em `drizzle/`; SQL custom (trigger em `auth.users`) via `drizzle-kit generate --custom`. Nunca `drizzle-kit push` em produção.
- **Tipos ↔ schema**: `camelCase` no TS, `snake_case` no Postgres; mudar uma tabela exige, no mesmo PR, `src/db/schema.ts` + migration nova + o mapeamento em `src/db/queries/*` ou no `adapters/` da fatia. Dinheiro em centavos (inteiro), nunca float.
- **Auth** com `@cbrl/supabase` (sobre `@supabase/ssr`, sessão em cookie; clients `null` quando `NEXT_PUBLIC_SUPABASE_*` falta — o app degrada): `/client` no browser (só Auth), `/server` no servidor; `src/proxy.ts` refresca a sessão (`updateSession`); `getServerUser()` (`@/lib/auth/server.ts`) usa `getClaims()` dentro de `readBackend`. **Nunca** confiar em `getSession()` no servidor.
- **Login (Google, redirect)**: `/` mostra "Entrar com Google" (`useGoogleSignIn`, `@/hooks`) → Google → `/auth/callback` (`authCallbackRoute`) → `next` (same-origin, padrão `/painel`). `/painel` sem sessão redireciona pra `/?login=1&next=…` e o `AutoSignIn` dispara o login. O perfil (`profiles`) nasce do trigger `on_auth_user_created`. Login de teste do E2E: `/api/e2e-signin`.
- **Degradação**: leitura de backend no servidor passa por `readBackend` (`@/lib/backend-read`, timeout + fallback); backend fora → estado "Tentar de novo".

**Proibições:** `@/lib/db`, `@/db`, `@/lib/auth/server`, `@cbrl/supabase/server`, `@cbrl/log` em client components; acessar o banco pelo client do Supabase (PostgREST); chave secreta do Supabase no app (só existe no stack local, pra E2E/seed).

## Não-óbvio

- **Deploy**: Vercel (Root Directory = raiz do repo; `vercel.json` com região `gru1` e cron diário em `/api/health`), Postgres/Auth no Supabase. Envs na Vercel: `POSTGRES_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. **Migrations em produção só pelo CI** (job `migrate-production` → `pnpm db:migrate`, no merge pra `main`); ninguém roda migrate contra prod da própria máquina. Toda migration é expand → contract e imutável depois do merge (o CI barra drift e edição). Runbook em [`docs/production.md`](docs/production.md).
- **Analytics**: `@vercel/analytics` só em produção, com URL redigida (`@/lib/web-analytics`): query e fragment nunca saem do browser; rota nova com id privado entra em `REDACTED_ROUTES`.
- **Testes**: `vitest.config.ts` (unit, jsdom; `src/db/*.test.ts` declaram `@vitest-environment node`; `src/db` e `src/features/*/adapters` fora da cobertura) e `vitest.pg.config.ts` (`src/**/*.pg.test.ts`, Postgres real, sem paralelismo, `server-only` trocado pelo shim do `@cbrl/testing`). E2E: um usuário por worker (`e2e/fixtures.ts`, `test.use({ authAsUser: true })`).
- **Isolamento do banco de dev (dados reais)**: o banco `postgres` do stack local guarda os dados financeiros importados do usuário; nenhum teste pode apagá-lo.
  - **Suíte Postgres** roda no banco `fluxi_test` do mesmo Postgres: `vitest.pg.config.ts` reescreve `POSTGRES_URL` (ou o `readLocalSupabase`) pra `/fluxi_test` e o `globalSetup` (`vitest.pg.setup.ts` → `prepareTestDatabase`, `src/db/test-database.ts`) cria o banco, um stub mínimo de `auth.users` (o schema `auth` do GoTrue só existe no `postgres`), espelha os grants dos papéis da API e migra — idempotente. `truncateFluxiTables` chama `assertTestDatabase`: exige URL local apontando pra `fluxi_test` **e** `current_database() = fluxi_test`. Custo: o stub não é o `auth.users` real do GoTrue (só as colunas que FK, trigger e `seedUser` tocam).
  - **E2E** precisa do Supabase Auth, então usa o banco de dev, mas só cria/apaga os próprios usuários (`e2e+w<N>@fluxi.local`; `recreateE2eUser` recusa outro e-mail). Nunca trunca tabela nem apaga outro usuário.
  - **`db:seed`** é idempotente e não destrutivo: cria o `dev@fluxi.local` só se faltar e semeia o ledger de exemplo só enquanto ele não tem bancos; nunca apaga nada.
- **Ledger (`src/features/ledger`)**: leituras em `adapters/ledger.repo.ts` (+ `views.ts`, loaders das páginas via `readBackend`; `projection.ts`), escritas em `adapters/ledger.write.ts`, server actions em `adapters/actions/` (validam com os schemas zod do `core/schemas.ts`, `userId` sempre da sessão), telas em `ui/` (a projeção roda no client sobre o `LedgerData` vindo do servidor). `core/` é a lógica portada do protótipo (sem I/O): `occursIn`/`landingsIn` (partes com `nextMonth`, dia limitado ao tamanho do mês, `skipped` some com a ocorrência e todas as suas partes; `deleted` = o usuário excluiu "Só este mês": também `skipped`, mas nunca aparece, nem em "Mostrar ignorados", que fica só com os meses pulados pela importação), `projectMonths` (saldos só acumulam a partir de `count_from_month`; meses anteriores vêm com `counted: false` e saldos `null`), `dailyBalance` e `applyScopedEdit` (`future` fora do 1º mês **divide** a série: a antiga termina em `mês-1` ou fica com as parcelas já vencidas; a nova começa no mês com o patch, as parcelas restantes, cópias das partes e os overrides dali pra frente). Meses no core são `YYYY-MM`; no banco, `date` no dia 1 (os adapters convertem). Parcelado guarda o **total** em `amount_cents`: `seriesAmountFor` divide em parcelas iguais (piso) com os centavos de sobra na 1ª; patch de valor numa parcela (`all`/`future`) vira `valor × parcelas`, e cortar a série (`endSeriesBefore`, usado no split e na exclusão `future`) leva junto a fatia do total. Partes dividem em bps com piso; se somam 10000, o resto do arredondamento vai pra última parte. `adapters/` é o único lugar que lê o ledger e **toda** função recebe `userId` e filtra por ele; FKs entre linhas do ledger são compostas `(id, user_id)`, então o banco recusa referência cruzada entre usuários. Testes Postgres das fatias moram ao lado (`*.pg.test.ts`, qualquer lugar de `src/`); adapters ficam fora da cobertura unitária, como `src/db`.
- **Pago/recebido (`occurrence_payments`)**: só status, nunca mexe no saldo projetado (a ocorrência já conta). Chave = entry + mês de competência (como `entry_overrides`) + `part_id` pra entry dividida (cada parte é paga à parte; `part_id` null = ocorrência inteira; unique `NULLS NOT DISTINCT`). Consistência nas escritas (`adapters/payments.write.ts`): partes são atualizadas in-place (`keepPartIds` + upsert em `replaceParts`), senão o cascade apagaria os pagamentos; depois de editar/excluir, `syncPayments` remove pagamentos sem ocorrência (mês excluído/pulado, série encerrada, inteira ↔ dividida); `future` que divide a série move os pagamentos do mês em diante pra nova entry (partes casadas por posição). "Hoje" é sempre parâmetro do core (`YYYY-MM-DD`); o servidor calcula com `todayIso()` em America/Sao_Paulo (sem fuso por usuário ainda). "A pagar" (`/painel/a-pagar`) olha do `count_from_month` (no máximo 12 meses atrás; antes disso é histórico não acompanhado, nunca "atrasada") até o fim do próximo mês; transferências aparecem com "Pago" e têm total próprio.
- **Benefícios contam como qualquer conta**: contas `benefit` (VA, VR, Vale Cultura, auxílio home office) entram em todos os totais, saldos, no calendário, em "A pagar", no painel e nos potes/semáforo (`MonthResult.totals` é um só, sem baldes). Para tirá-las de uma visão, filtre: calendário/dia a dia por banco ou conta (`decisionAccountIds`), e em `/painel/lancamentos` o filtro "Dinheiro" (`core/bucket.ts`: Disponível × Benefícios; padrão Tudo). Já houve a regra oposta (visões de decisão só com o "disponível"); foi removida porque os filtros cobrem o caso sem esconder dinheiro por padrão. A lista de lançamentos carrega o ledger inteiro uma vez (`ledgerSpan`: séries sem fim até hoje + 12 meses) e filtra no client, então busca e filtros nunca vão ao banco; a consulta fica num cookie do browser (`fluxi_lancamentos`, escrito pelo client e lido pelo servidor pra renderizar já filtrado), não no Supabase nem na URL.
- **Orçamento: potes editáveis e versões (`core/budget.ts`)**: potes vivem em `pots` (chave `key` estável; os 6 semeados mantêm as chaves históricas `essential`… e potes novos ganham `p_<10 chars>`), com nome, cor (paleta fixa `POT_COLORS`, classes literais em `core/labels.ts` pro Tailwind enxergar) e `goal` (`limit` = gastar até a meta; `minimum` = guardar ao menos, semáforo invertido). `entries.pot` e `categories.default_pot` são `text` com FK composta `(pot, user_id)` → `pots`. Excluir pote em uso (lançamento ou categoria) **arquiva** (some dos pickers, fica no histórico); sem uso, apaga junto com as metas. As metas ficam em versões (`budget_plans` + `budget_plan_targets`, bps da renda, soma ≤ 100% checada no adapter): a versão em vigor num mês é a última que começa nele ou antes (`planFor`); meses antes da primeira versão ficam **sem meta** (cinza, sem luz) em vez de serem julgados pela proporção atual. Mudou a proporção (aluguel, aumento, filho): "Nova versão…" a partir do mês, e os meses anteriores seguem medidos pela versão deles. CRUD inline no card "Potes da renda" (`ui/budget/`); `/painel/orcamento` e `/painel` carregam o ledger inteiro e projetam no client, então as setas do semáforo não vão ao servidor. A tabela `budget_pots` (metas fixas antigas) não é mais lida: fica até a migration de contract.
- **Defaults por usuário vêm do trigger, não do app**: `public.seed_budget_defaults(uid)` (migration `0010_budget_pots_plans`: os 6 potes e a 1ª versão de metas) e depois `public.seed_ledger_defaults(uid)` (migration `0003_ledger_defaults`: categorias, que apontam pros potes, `budget_pots` legado e `user_settings`) rodam dentro do `on_auth_user_created`, na mesma transação do perfil. Escolhido em vez de semear sob demanda no app porque vira invariante do banco (todo perfil tem potes/categorias, sem `ensureDefaults` em cada request nem corrida entre requests concorrentes, e vale pra qualquer caminho que crie usuário: Google, `seedUser`, E2E). Custo: a lista vive em SQL imutável; mudar `DEFAULT_POTS`/`DEFAULT_CATEGORY_GROUPS` (`core/defaults.ts`) exige migration nova que substitua a função correspondente — a suíte Postgres compara o seed com as constantes e falha se divergirem. As funções são idempotentes (`ON CONFLICT DO NOTHING`) e não executáveis pelos papéis da API.
- **Importação do Notion (`src/features/import`, `pnpm import:notion -- --email <e-mail> [--dry-run]`)**: `core/` transforma as páginas cruas em plano (agrupa linhas em séries mensais/anuais com overrides e meses pulados, pareia transferências "Mesma titularidade", mapeia categorias/potes) e prova que é sem perda re-expandindo com o `landingsIn` do ledger (0 divergência por mês × conta × movimento, senão sai ≠ 0 e não grava). Única exclusão deliberada (`core/mirrors.ts`, antes do agrupamento): saídas-espelho FUTURAS em conta de benefício (mês ≥ `COUNT_FROM_MONTH`, sem `Date`, mesmo valor de uma entrada da mesma conta e mês; uma entrada cancela no máximo um espelho), que só existiam pra compensar o saldo inflado; espelhos passados/pagos ficam como histórico. A verificação compara com os originais menos esse conjunto explícito (`expectedFlows`) e o relatório diz quantos saíram; as linhas continuam no `import_raw`. `adapters/` lê a API do Notion (`NOTION_TOKEN` ou `~/.config/fluxi/notion.env`) e grava numa transação só: apaga o que a importação anterior criou (entries via `import_links`; bancos/contas/categorias via `import_raw.target_id`, só se nada mais usa) e reinsere. `import_raw` guarda TODA página lida (inclusive ignoradas). Alvo = `POSTGRES_URL` se definido, senão o stack local. LGPD: o relatório só imprime agregados; dados reais nunca em fixture/commit (testes usam o workspace sintético de `core/fixtures.ts`).
- **Origem**: criado em 2026-11-24 a partir do baseline de infraestrutura do `imovil` (sem o domínio de imóveis).
